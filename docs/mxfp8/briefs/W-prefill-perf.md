# Brief W — Why is prefill at ~5–10% of hardware peak? Profile it, don't guess it

## The claim to explain

`llama-completion -m ~/models/timlikesai/Inkling-2-Mini-NATIVE.gguf -c 8192 -f logs/g0-prompt-long.txt -n 64 --temp 0 -no-cnv -s 42` gives **prefill ~507–509 t/s** and decode ~22 t/s. Arithmetic from measured config (24 weight layers, 48 layer applications, 3.1 B active params, 14.6 GiB of expert weights, 17.66 GiB total, `n_batch` default **2048** per `common/common.h:479`):

- ~6.2 GFLOP/token × 509 t/s ≈ **3.2 TFLOP/s**, versus tens of TFLOP/s of f16 MMA on two RTX 5060 Tis and several× that in fp8/fp4 → **single-digit % of peak**.
- Weights are read once per 2048-token batch ⇒ 8.6 MB/token ⇒ **~4.4 GB/s** → also nowhere near ~450 GB/s/card.

**Neither axis is saturated, so the model is stalled on something structural.** That's the thing to find. Tim's list of suspects (all live, all testable) is below, plus two I'd rank higher than the rest.

## Tooling — real profilers are installed

`/usr/local/cuda/bin/nsys`, `/usr/local/cuda/bin/ncu`, plus `compute-sanitizer` and `cuobjdump`. **Use them; do not infer from wall clock alone.** A single `nsys profile -o logs/w-nsys-prefill --force-overwrite=true ./build-cuda/bin/llama-completion ...` will show gaps between kernels and any `cudaMemcpy`/sync serialization; `ncu --set full -k regex:mul_mat_q` on a small repro gives occupancy, DRAM %, and stall reasons. Both binaries run fine here — check `--version` first and keep outputs in `logs/`.

## Hypotheses, ranked by how much I'd bet on them

1. **`MUL_MAT_ID` forces device syncs, serializing the 48 MoE applications.** Start in `ggml/src/ggml-cuda/ggml-cuda.cu::ggml_cuda_mul_mat_id_needs_sync` and `ggml_cuda_mul_mat_id` — note there is a `[TAG_MUL_MAT_ID_CUDA_GRAPHS]` tag and `moe_cache->get_experts(w)` with `slots` in the graph path (`src/llama-graph.cpp:1894-1896`). If each MoE layer round-trips to the host, that alone explains 10×. **Evidence to produce:** nsys timeline showing gaps at every layer, or a sync counter.
2. **The per-expert `.scale` is applied as a full-size elementwise `MUL`, i.e. we move the whole MoE output an extra time per layer.** `build_lora_mm_id` does `reshape → repeat_4d → get_rows(ids) → ggml_mul(res, s)` on a `[n_ff(2304), n_expert_used(8), n_tokens]` tensor, 48× per pass. The scale is **one float per expert** — a scalar per row-group, so a full-tensor multiply is pure waste. Check whether it can fold into the routing weights (`selected_experts` already gets scaled by `w_scale`/`route_scale`) or into the GLU epilogue. **This one is plausibly ours to fix and is a direct "we are moving memory around in a bad way" hit.**
3. **Flash Attention is silently OFF with the 2-card split.** Measured by a sibling lane at `-c 2048`: `resolve_fused_ops: layer 24 is assigned to device CUDA1 but Flash Attention is assigned to device CUDA0` → `Flash Attention not supported, set to disabled`. Without FA, prefill attention materializes scores (extra traffic + kernels) and KV stays f16. Try `-sm layer` vs `row`, `-ts` splits that keep attention on one card, `--flash-attn on` explicit, and single-card with `--n-gpu-layers auto` after `--override-tensor` to see the ceiling. **Quantify the delta** — at 2817+ tokens this could dominate.
4. **The MXFP8 activation quantizer may be scalar.** Tim's specific suspicion: "we may be using scalar quantization of the activations to mxfp8 when intrinsics are available." Read `ggml/src/ggml-cuda/quantize.cu`'s new e4m3+ue8m0 path (added in `c39ab0a00`, ~119 lines) and check: are floats loaded as `float2`/`float4`; is the per-32 `amax` reduced with `__reduce_max_sync`/`__shfl_xor_sync` or a naive loop; is the e4m3 conversion done with `__nv_cvt_float2_to_fp8x2` (packed) or per-element; is the ue8m0 scale derived by bit tricks or a `log2f/ceilf/exp2f` trip through SFU; and is the `+0.5f` rounding preserved. Compare against the tuned `quantize_mmq_mxfp4` and against how `to_q8_1` vectorizes — the FP4 version is the performance reference on this box.
5. **Tiling/warp configuration for MXFP8 MMQ was mirrored, not tuned.** `c39ab0a00` gave MXFP8 the same `J`/occupancy/`I` entries as MXFP4 (`mmq-config-blackwell.cuh`) because the geometry matched — that makes correctness easy and leaves performance unexplored. Sweep `J` (and the fallback vs non-fallback variants) at the real shapes (`K=2304`, `N=2304/1152`, `E=128`, `n_expert_used=8`), and check `ncu` for achieved occupancy, `smsp__warps_issue_stalled_*`, and DRAM throughput. Also confirm the loader's `threads_per_row = iter_k/QK_MXFP8 = 8` is actually efficient (one thread per 32-byte block via `memcpy` — is it a coalesced 32B/thread access or 8 separate byte loads?).
6. **The NVFP4 path may be running in a slower mode than its best one.** Tim: "with the nvfp4 weights it should be quite fast through the existing nvfp4 x4 mma path". Verify which kernel the 20 NVFP4 layers actually execute during prefill: `kind::mxf4nvf4.block_scale.scale_vec::4X…ue4m3` (W4A4) vs the `GGML_PREC_Q8`/`BF16` variants. Note `src/llama-graph.cpp:1900-1904` sets `ggml_prec_set_acc(res, GGML_PREC_BF16)` for NVFP4 weights and `prec_src1` selection lives in `ggml/src/ggml-cuda/mmq.cu::ggml_cuda_mmq_get_prec_src1`. **Measure NVFP4-only and MXFP8-only prefill separately** (e.g. by building a file variant, or by timing a synthetic `MUL_MAT_ID` at both types with `test-backend-ops`-style harness) so "prefill" isn't one blended number. Also sanity-check the claim itself: our native file prefills at 509 t/s vs the lossy IQ4_NL file's 492 t/s, so we are not slower than the reference — the question is whether *both* are 10× off, which points at the model plumbing rather than our MXFP8 work.
7. **Graph capture / scheduling.** `graphs reused = 94, reallocs = 0` looked healthy, but check `GGML_CUDA_GRAPH_CHUNK_SIZE`, `GGML_CUDA_GRAPH_OPT`, whether the MoE path is inside or outside the captured graphs, and whether `--moe-cache` modes change prefill (there is a `llama-moe-cache.cpp` with slot maps that may be doing host-side work per batch).

## Method

1. **Write `docs/mxfp8/22-prefill-perf.md` in your first 4 tool calls** with: this claim, your hypothesis ranking, and a results table to fill in. Then update it after every measurement. A doc that says "hypothesis 3 disproved, here's the number" is a success.
2. **Establish a repeatable micro-benchmark** before changing anything: prefill t/s on the real file (fixed corpus slice), plus a synthetic `MUL_MAT_ID` at Inkling's exact shapes for `nvfp4`, `mxfp8`, `q8_0` and `f32` so kernel-level cost per type is visible in isolation. Everything you report references this harness.
3. **Isolate before optimizing.** Order of operations: profile (nsys gap analysis) → identify the dominant stall → fix that one thing → re-measure. Do not stack three changes and then try to attribute.
4. **Correctness is a hard gate on every change**: `llama-completion -m <NATIVE> -c 4096 -p "Q: What is 17 times 4? A:" -n 24 --temp 0 -no-cnv -s 42` must print `A: 68 B: 64 C: 72 D: 70 E: 66 F: 69 G:` on CUDA **and** `-ngl 0` on CPU, and `test-backend-ops -p mxfp8` must stay 237/237 on CUDA0 and CUDA1 with CPU 306/306. Any change that alters the string is a bug, not a tradeoff.
5. If you find a fix worth landing, commit it separately with before/after numbers. If you find a structural problem in upstream's MoE/loop plumbing, **document it precisely with a minimal reproducer** — that's PR-worthy material for llama.cpp and is as valuable as landing code here.
