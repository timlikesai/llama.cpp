## Five cautions that cost real time this session

1. **A fitted coefficient is not an explanation.** Doc 29 fitted "3.5 f32 copies" convincingly; a dtype halving then moved the slope by exactly 0.0%. The *ablation* (delete the node, measure) was the proof — and the reason was one line: `ggml_get_rows` hard-codes an F32 return. Read the op before theorizing about the allocator.
2. **Check whether the code you are blaming is yours.** `n_layer_all` (48) vs physical layers (24) caused the placement bug *and* the loop-slot scale bug. Before adding a pass, grep upstream — `690b87d88` had already fixed our "mysterious" numeric bug while I was building an elimination campaign.
3. **Measurement traps documented the hard way:** never pin a nonzero `-ngl` (disables auto-fit — the docker crash-loop's actual cause); `llama-bench` never runs the fitter; the KV cache type string is `f8_e4m3` (`fp8` dies in argument parsing); read **both** iswa `llama_kv_cache: size =` lines; at long context only the **final** `sched_reserve` pass is valid; in `llama-perplexity` `-b` must equal `-c`; `--spec-*` are example-gated (`SPECULATIVE|SERVER|CLI|IMATRIX`, not `llama-completion`); **`-no-cnv` belongs to `llama-completion` and is an invalid argument for `llama-cli`** (which has only `-st/--single-turn`) — I twice wrote `-no-cnv` into `llama-cli` invocations from memory and each time the process exited on `error: invalid argument`; `llama-cli` prints `[ Prompt: x t/s | Generation: y t/s ]` while `llama-completion` prints `prompt eval time`; **an image request whose connection just drops is a server crash, not a client error — read `RestartCount` and the CUDA error in the log**; and **a harness process that printed its summary may still be alive** (`--jinja` leaves `llama-cli` in conversation mode waiting on stdin, holding 21 GB) — always `< /dev/null`, and check `nvidia-smi --query-compute-apps=pid,used_memory,process_name --format=csv` before believing any allocation failure.
4. **An `E`-prefixed line containing the words "failed to" is not necessarily fatal.** `llama_init_from_model: failed to initialize the context: dflash requires ctx_other to be set (this warning is normal during memory fitting)` is printed by design during the fitter's first probe — my error regex matched it and reported six perfectly good runs as failures (and earlier, made me think a regression existed). Test for `exiting due to`, `GGML ASSERT`, `core dumped`, or `error: out of memory`; and check for the actual result line (`eval time =`) before concluding anything.
5. **Measure a kernel's share before optimizing it.** The MXFP8 MMQ path cost a full session to build and is **1.8%** of decode device time (4 of 24 layers, and its tile loader is only worth ~1% even at 2×). The dominant decode owner turned out to be two bf16 vocab matrices at 2.19 ms each. Had I profiled share-of-time first, the ordering of the whole evening would have been different.

6. **A conflict-free auto-merge is not a semantic pass.** Upstream's `#32740` added an unconditional
   `return BEST_FATTN_KERNEL_NONE` for indexed bias; our real dispatch sat ~90 lines later. Git merged
   both without a conflict, the build was green, the tests were green, and 23% of prefill was gone. After
   any rebase that touches a capability, measure the thing the capability was supposed to make fast.
7. **Two more instrument failures, both mine, both silent.** (a) Without `-v`, this `llama-cli` build writes *only warnings* to its log — I read three 155-byte files as "no problem found" when they contained no data at all; with `-v` the `[ Prompt | Generation ]` summary vanishes in favour of `print_timing`, so the two modes need different parsers. (b) `grep DONE` against `tmux capture-pane` matches the **echoed command line**, so a job I thought finished had merely been typed. Use a marker file (`touch logs/.done`), not a sentinel string.
8. **`pkill -f <pattern>` matches your own shell.** Twice it killed the command that was running it (exit 143), because the pattern appeared in its own `bash -c` argument. To clean up GPU processes: enumerate `nvidia-smi --query-compute-apps=pid`, then check `/proc/<pid>/cgroup` for `docker` before killing — that also guarantees you never kill the deployed container.

## Verify flag names, never recall them

Every wasted run in the last two sessions came from a remembered flag that this build does not have (`-no-cnv` on `llama-cli`, `--moe-fused-sum`, `--nobd`, `-ns`, `--pg`, `--chunk`, `-o` on `llama-perplexity`, `fp8` instead of `f8_e4m3`).
